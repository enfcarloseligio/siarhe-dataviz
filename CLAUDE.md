# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

WordPress plugin (`siarhe-dataviz/`, the plugin root is the nested folder) that renders choropleth maps (D3.js v7) and tables of Mexican nursing human-resources data (SIARHE). UI text, comments and identifiers are in Spanish; match that. Requires WP 6.0+, PHP 7.4+ (declared in the plugin header and checked at load time; see `docs/requisitos.md`).

There is **no compile step, package manager, linter or test suite**. The only tool is the packager `build.ps1` at the repo root (versioned in git; its output `builds/` and `*.zip` are git-ignored): run `.\build.ps1` to get `builds\siarhe-dataviz-<SIARHE_VERSION>.zip` (reads the version, warns if the header `Version:` differs, strips `*.md`/logs/scripts/`vendor`/`node_modules`/`.git*`, empties `uploads/` keeping `.gitkeep`, writes `/` paths in the zip). Development = edit PHP/JS/CSS and reload in a WordPress install that has the plugin folder in `wp-content/plugins/`. Version is declared twice in `siarhe-dataviz/siarhe-dataviz.php` (plugin header and `SIARHE_VERSION`); bump both together (commit messages follow the version, e.g. `0.0.5.42`).

## Documentation

Project documentation lives in `docs/` (repo root, not shipped in the plugin zip): requirements, architecture, admin screens, data formats, map performance, design decisions, release procedure and tests. `CHANGELOG.md` has the version history. Keep them updated when behavior or formats change.

## Architecture

**Backend (PHP)**
- `siarhe-dataviz.php` defines constants (`SIARHE_PATH/URL`, `SIARHE_UPLOAD_DIR/URL` → `wp-content/uploads/siarhe-data/{geojson,raw,processed,static-min}`), loads modules, and boots `Siarhe_Admin` and `Siarhe_Shortcodes` on `plugins_loaded`. Activation installs tables via `Siarhe_DB_Installer` and creates the upload folders.
- `includes/class-siarhe-shortcodes.php` registers shortcodes dynamically per entity from `siarhe_get_entities()` (`includes/helpers.php`): `[siarhe_mapa_{M|T|MT}_CVE_ENT_{nn}]` (M = map, T = table, MT = both; `33` = national). `render_viz()` looks up the active GeoJSON and "static_min" CSV for the entity in the `{prefix}siarhe_static_assets` table (`es_activo = 1`) and includes `public/partials/siarhe-view.php`.
- `public/partials/siarhe-view.php` is the real frontend entry point: it enqueues the JS modules conditionally by mode, reads all admin config options, and emits a container whose `data-*` attributes (`data-geojson`, `data-csv`, `data-marker-config`, `data-metricas`, `data-tooltips`, …) carry configuration to JS as JSON. Script versions are each file's `filemtime`, so browsers cache them until they change.
- `admin/class-siarhe-admin.php` handles uploads/updates/deletes through `admin_post_siarhe_*` actions (GeoJSON, localidades, static CSV, markers) and registers settings options: `siarhe_map_options` (colors), `siarhe_theme_options`, `siarhe_links_map`, `siarhe_metricas_config`, `siarhe_tooltip_config`, `siarhe_marcadores_config` (JSON string). UI lives in `admin/partials/` (settings split into `settings-tabs/` and `upload-tabs/`). `admin/partials/siarhe-settings.php` is one template shared by two menu screens: **Personalizar** (`siarhe-customize`: tabs `tema`, `mapa`) and **Configuración** (`siarhe-settings`: `enlaces`, `tooltip`, `metricas`, `marcadores`); tab slugs/option groups are declared at the top of that file.
- `includes/db/` holds the installer (`dbDelta`), data loader and query classes.
- `enqueue_frontend_scripts()` in the shortcodes class registers the frontend CSS (with the single `:root` variables block from `siarhe_get_css_variables_css()` in `helpers.php`, which also holds the shared defaults and entity catalog) and registers D3 from its CDN. `siarhe-core.js` (`app.ensureD3`) falls back to the bundled copy in `public/js/libs/` if the CDN fails; Select2 in the admin has the same CDN-first/local-fallback pattern (`admin/libs/`). Do not name folders `vendor/` (ignored by git and excluded from the build zip).

**Frontend (JS, `public/js/`)** — plain scripts (no bundler) sharing one global namespace `window.SiarheDataViz` (`app`). Load order is enforced through WP script dependencies in `siarhe-view.php`:
`siarhe-core.js` (state, `app.utils`, `app.math`, `app.data` CSV/GeoJSON loading and metric computation, `app.initVisualization(container)` which parses the `data-*` config) → `siarhe-controls.js` (`app.controls`: selectors/filters UI) → `siarhe-tooltips.js` (`app.tooltips`) → `siarhe-map.js` (`app.map`, D3 SVG map, zoom, markers, fullscreen) and `siarhe-table.js` (`app.table`). Map and tooltips scripts load only when the mode includes `M`; table only for `T`. Map colors come from CSS variables (`--s-map-*`, `--s-th-*`, …) injected by `wp_add_inline_style` from `siarhe_map_options` and read in `core.js`.

Marker names/labels and metric definitions are configured dynamically in admin options (not hard-coded in JS); keep new marker/metric behavior driven by those configs.

Marker `tipo` values: `posicion` (fixed symbol), `espectro` (bubble sized by value) and `spike` (triangle whose height and color follow the value; the picked color is the tallest spike and lower values fade toward `fill2` or a lightened version). Espectro and spike share the "Densidad" selector (`app.utils.markerGroup`) and the numeric column config (`espectro_col`). Marker geometry for all types lives in `app.map._markerShape` (used by the initial paint and the zoom handler). Marker colors (`m_<key>_fill`, `m_<key>_fill2`, ...) are edited in Personalizar > Mapa & Colores; data/behavior in Configuración > Marcadores.

Distance measuring (`app.map.initMeasure/setMeasureMode/measureAddPoint/renderMeasure`, only created when a `posicion` marker exists): toolbar ruler button toggles a mode where clicking position markers measures straight-line (great-circle) distances in two types (`ms.mode`): `chain` (route A→B→C with per-leg and total, up to 10 points) and `radial` (first marker is the center; each other marker gets its own independent distance, up to 20, with nearest/farthest summary); clicking an already-selected marker removes it (route A-B-C becomes A-C; in radial mode removing the center promotes the next point); the panel can copy the result or download it as UTF-8 CSV (`_measureCsv`, one row per point; text fields are guarded against Excel formula injection); the SVG layer `gMeasure` redraws on zoom with constant label size and a results panel (`.siarhe-measure-panel`) lists legs/total with undo/clear/copy. Spike and espectro markers are deliberately not measurable.

Stacked markers (`app.map.stackBind/_cvStackAt/_svgStackAt/stackClick/stackShow/stackClose`, panel `app.tooltips.showStackCard`): ONE capture-phase click listener on the main svg handles marker clicks in canvas and SVG mode (the old per-mode click handlers were removed). On click it collects the markers covering the tapped one (computed only then, never on hover); 1 marker = old behavior (select for measuring), 2+ = tappable card `.siarhe-stack-card` with "n de N", prev/next, numbered list and, while measuring, an add/remove button; repeated clicks at the same spot cycle. Nothing is merged. The selected one is highlighted via `cv.sel` (canvas) or a thick stroke (SVG). The hover tooltip is suppressed while the card is open; the card closes on pan/zoom by the user, on clicking elsewhere and when the points change.

## Static bases: year, unit and CSV/JSON (0.1.2.0)

A static base is **entidad + año + unidad** (`plazas` | `personas`); table `siarhe_static_assets` (schema v2, `Siarhe_Admin::DB_VERSION`) has `unidad` and `ruta_json` next to `ruta_archivo` (CSV). Files are flat in `static-min/` as `{slug}-{año}-{unidad}.csv|json` (flat so versions and read copies keep working). The upload form (`tab-static.php`, custom, not `_uploader.php`) takes a year select (2006 on; `Siarhe_Static_Json::YEAR_MIN`) and a unit select, and accepts CSV or JSON: the uploaded one is validated and the other is generated (`Siarhe_Static_Json::from_csv` / `to_csv`, same algorithm as RHEMX's `src/estatico_json.py`; JSON `anio`/`unidad` must match the form), so both always exist and are equivalent. The migration assigned the bases loaded before this to year 2026, plazas, and built their JSON. The shortcode serves the latest year in plazas first and hands every base of the entity to the front end in `data-bases` (`{año: {unidad: {url, fecha}}}`, JSON preferred); `app.controls.buildBaseSelectors` adds the year and unit selects (only with more than one option), `app.data.loadBase` / `setBase` swap the data and the URL hash carries `a` and `u`. The year select goes up to the current year (`gmdate('Y')`). The 62 RHEMX variables (estudios with LEO, `esp_*`; `includes/metricas-rhemx.php`, generated from RHEMX's `diccionario_variables.csv`) are default metrics flagged `opcional`: hidden from the indicator select when the loaded base lacks the column (`syncIndicatorOptions`, `state.columnas`) and skipped by the upload warning; `siarhe_get_metricas_config()` merges missing native metrics into a saved config. **Temas** (0.1.5.0): option `siarhe_temas_config` `{clave: {label}}` (`siarhe_get_temas()`; `general` always exists, defaults `estudios` and `especializacion`); every metric has `tema` (missing = `general`, so the original metrics are in General); managed in Configuración › Métricas (Temas card + a Tema select in the metric modal); the front end has a Tema select before the indicator (`buildThemeSelector`, `data-temas`) that filters the indicator list together with `opcional`/columns. JSON options are read with `siarhe_decode_json_option()` (raw first, `wp_unslash` only as fallback; it also repairs the damaged `u00f3` text), never with a bare `json_decode(wp_unslash(...))`. **Indicators** (0.1.6.0): the indicator select lists each indicator once by its short `nombre` (`app.controls.indicatorName`) and the **Medida** switch (`buildMeasureSwitch`, `state.medida`, `metricFamily` groups tasa+frecuencia by `pair`) toggles between the rate and the count (`tipo` `tasa` / `absoluto`, shown to users as Tasa / Frecuencia); a family lacking the chosen measure is still listed with the one it has. The metric `descripcion` is shown under the select with `{unidad}`/`{Unidad}` replaced by plazas/personas (`updateIndicatorDesc`); the unit select is always visible (disabled with one option). The 143 default metrics are **system** metrics (`is_core`): `siarhe_get_metricas_config()` forces their name, texts, type, pair and theme on every read and keeps only `visibilidad` and scale/range/colour fields; the panel locks them. System themes (`siarhe_get_temas()`, flag `sistema`): General, Nivel de atención (`nivel_atencion`, primer/segundo/tercer/apoyo/administrativas/escuelas/otros/no asignado), Estudios, Especialización; users add their own themes, also from the metric modal. Tooltip config is JSON (`register_setting(..., $json)`; it was wrongly registered as an array from 0.0.5.45 and never persisted). Control icons are RHEMX's line SVGs in `public/img/`, painted with a CSS mask (`addControlIcons`). Marker CSVs accept the CLUES catalog headers (`CLAVE DE LA ENTIDAD`, `CLAVE DEL MUNICIPIO`, `CLAVE DE LA LOCALIDAD`, `NOMBRE DE LA INSTITUCION`, `NOMBRE TIPO ESTABLECIMIENTO`, `NOMBRE DE TIPOLOGIA`) in the worker, the main-thread fallback, the tooltips and `validate_csv_file`. PHP can be tested without WordPress with a portable PHP 7.4 (windows.php.net archives) in a scratchpad.

## Geometries by marco, markers by period (0.1.7.0)

Written and unit-tested on 2026-11-12 with Node and PHP 8.4 (`C:\php\php.exe`) against RHEMX's real files (`tests/`, see `tests/LEEME.md`); **not yet tried in a real WordPress**.

- **Geometries are TopoJSON by marco.** *Geolocalización* (base layer, `tipo_archivo` `geojson`) and *Localidades (Geo)* (detail layer, `localidades_geojson`) take RHEMX's TopoJSON (`.json` / `.topojson`: object `datos`, properties `c`, `n`, `t`) and keep one file per entidad + marco quinquenal (`anio_reporte` = 2005, 2010, 2015, 2020, 2025; `Siarhe_Geo::marcos()` adds 2030 when that year arrives; the 2016 marco goes in 2015). Files are `{entidad}-{marco}.json`. `Siarhe_Geo` (`includes/class-siarhe-geo.php`) holds the marco rule (`marco_para`: the year's quinquenio, else the closest earlier one, else the oldest), the TopoJSON validation (`validar_topologia`: layer by the digits of `c` — 2 entidad, 5 municipio, 9 localidad — and entidad by its first two; AGEB and wrong-layer files are rejected) and `archivos( $slug )`. Which file goes where: nacional base `33_entidades.json`, state base `NN_municipios.json`, nacional detail `33_municipios.json`, state detail `NN_localidades.json` (taken from RHEMX's `data/processed/geo/<marco>/Capa 1 Geolocalizacion/` for the first two and `.../Capa 2 Localidades/` for the last two). Both tabs share `_uploader.php` and the handlers `handle_geo_upload / handle_geo_meta_update / handle_geo_delete( $capa )`. DB version 3 (`Siarhe_Admin::DB_VERSION`) assigned every geometry loaded before to marco 2025; old GeoJSON FeatureCollections are still read.
- **Front end:** `public/js/siarhe-topo.js` (`self.SiarheTopo`, shared by the page and the geo worker through `importScripts`) converts the topology with the bundled `topojson-client` 3.1.0 (`public/js/libs/`, loaded on demand; URLs in `window.SiarheDataVizConfig.topojson / topoHelper / capas`), turns `c`/`n`/`t` into the property names the map already used (`CVE_ENT`, `CVE_MUN` 3 digits, `CVE_LOC`, `NOMGEO`, `NOM_ENT`, `NOM_MUN`, `NOM_LOC`, `AMBITO`) and rewinds rings inverted by quantization (`d3.geoArea` > 2π). `app.geo` in `siarhe-core.js` loads geometries (`app.geo.load`), picks the marco (`marcoFor`, `locUrl`) and updates the footer source (`.siarhe-geo-ref`, `.siarhe-geo-date`). The shortcode sends every marco in `data-geos` (`{ base: { marco: { url, fecha, ref } }, loc: { marco: { url } } }`). Changing the year to another quinquenio calls `app.controls.applyMarco` → `app.map.swapGeography` (base polygons redrawn by `_drawBase`, projection, zoom, legends and markers kept; the detail layer is dropped and the view returns to base; `state._kbdRefresh` re-reads the keyboard node list); `syncDetalle` enables or disables the detail option per year.
- **Markers by period, CSV or JSON.** Each marker file type (`siarhe_marker_types()`: CATETER, HERIDAS, ESTABLECIMIENTOS and the admin's own) has one file per period: a year or `total` (all the history; `anio_reporte` 0), stored as `markers/{type name}-{periodo}.csv|json` with `ruta_json`. `Siarhe_Marker_Json` (`includes/class-siarhe-marker-json.php`) converts both ways and validates: the JSON is RHEMX's layer format (`fila` = field of each position, text lists `instituciones`, `niveles`, `tipologias`, `estratos`, `tipos_establecimiento`, `jurisdicciones`, `municipios`, `localidades`, and `unidades`; rows may omit trailing empty fields, e.g. `anterior`); a JSON built from a CSV adds `columnas` (original header of each known field) so both formats give exactly the same columns; the CSV→JSON pass is streamed. RHEMX files load unchanged (`unidades_clues_<año>.json`, `clinicas_cateteres_<año>.json`, `..._historico.json`, `clinicas_heridas_historico.json`). In a marker CSV only coordinates and the entidad key are required now. `public/js/siarhe-capas.js` (`self.SiarheCapas.aTabla / aObjetos / normaliza`) gives the worker and the main-thread fallback the same `{ header, rows }` table as the CSV. `data-marker-urls` is `{ marker: { periodo: url } }` (`siarhe_get_marker_file_urls()`, JSON preferred; markers without a loaded file are not offered); `app.controls.markerUrl` picks the year's file, else `total`, else the closest earlier year, and `refreshMarkersForYear` reloads the active markers after a year change. Column names in marker configs are compared ignoring case, accents and underscores (`nivel_atencion` = `NIVEL ATENCION`).
- **System markers:** `siarhe_get_default_marcadores()` / `siarhe_get_marcadores_config()` (`helpers.php`, the only way to read the marker config). `ESTAB_1`, `ESTAB_2`, `ESTAB_3`, `ESTAB_6`, `ESTAB_NE` (flag `sistema`) are «Establecimientos de Salud: Primer Nivel / Segundo Nivel / Tercer Nivel / No Aplica / No Especificado» (RHEMX's texts), filter `nivel_atencion` by that text and are forced on every read; the panel only lets their visibility change.
- **Controls:** the selector is labelled «Indicador» (was «Indicador Principal») and the description note under it was removed (`updateIndicatorDesc` no longer exists; the metric `descripcion` stays in the config). The Medida switch declares background and text colour together in every state, because site themes give `button:hover` white text.

## Roadmap / pending work

Agreed direction: this is the **static** version of the map (admin uploads GeoJSON + CSV). A **dynamic map backed by SQL** comes later; the admin "Gestor de Bases" is where it will live.

### Admin (backend) overhaul — proposed, awaiting go-ahead

Findings that motivate it: the action buttons in the upload tables misalign (inline `<form style="display:inline">` around the delete button + `.button-small` + dashicons baselines; fix with a flex row); Dashboard and Gestor de Bases are identical 6-line placeholders; partials total ~5,500 lines mixing PHP, inline JS and 20–90 inline `style=""` attributes each (400+ overall); the three upload tabs (geojson/localidades/static) are ~90% duplicated (~530 lines each); `siarhe-admin.css` is only ~275 lines with no design tokens; `tab-mapa.php` refreshes previews with a 400 ms `setInterval`; the UI uses native `alert()`/`confirm()`; no loading/empty states or upload progress.

Open decisions (recommended defaults in bold):
1. Style: **stay inside the WordPress admin look with a modern component layer** (cards, tokens; respects WP admin color schemes and dark modes) vs. a fully custom app-like skin.
2. Order: **Phase 1 + Phase 2 (Dashboard) first, then Phase 3, Gestor de Bases last.**

Phases:
- **Phase 1 – design system + fixes:** CSS variables (colors, spacing scale, radii, shadows) and reusable components (cards, buttons, badges, tables, grid forms); flex `.siarhe-row-actions` with uniform sizes; move inline styles to classes; consistent page header (title, description, actions); replace `alert`/`confirm` with a modal + toasts; replace the preview `setInterval` with events; responsive on mobile.
- **Phase 2 – real Dashboard:** 34-entity matrix showing which have GeoJSON / CSV / localidades / markers and last update; copy-shortcode button per entity (`[siarhe_mapa_MT_CVE_ENT_09]`); health checks (upload dir writable, `upload_max_filesize`, PHP memory, plugin version, D3 CDN reachability).
- **Phase 3 – unify and improve uploads:** one parametrized upload component for GeoJSON/localidades/static CSV; drag & drop, progress bar, preview of the first rows before uploading; **version history UI with restore** (the last 3 versions already live in `_versions/` but there is no UI to use them); search/filters on every table.
- **Phase 4 – Gestor de Bases (dynamic map):** ingest CSV/XLSX into SQL in batches of 50 or 100 rows via AJAX (`admin-ajax`, nonces + `current_user_can`) with progress, resume, validation report and import log. Reuse the Phase 3 upload component and the existing CSV validation (`validate_csv_file`).

Additional admin ideas: export/import of the whole configuration as one JSON (colors, metrics, markers, tooltips) to move staging → production; audit log ("who uploaded/changed what"; today only the last editor is stored); a dedicated plugin capability so editors can upload data without being administrators; "restore defaults" button for the color settings.

### Map / frontend — known open items
- Spike markers: heights are fixed at 25–100 viewBox units (×1.5 on touch), linear between the marker's min and max value. Possible follow-ups: make max height and scale type (linear / square root / percentile cap) configurable in Personalizar; with outliers most spikes sit near the minimum height. Heights are not comparable across entity pages (min/max are computed per loaded dataset).
- Markers have no keyboard focus (thousands of points); selection for measuring is mouse/touch only. The measure panel is the accessible part (live announcements, copy, CSV).
- On non-fullscreen mobile the legends top out around 6 px text because of the map's small width; fullscreen gets ~10 px.
- D3/Select2 CDN fallback only triggers on failure or an incomplete library; a very slow (not failing) CDN waits for the browser timeout (no explicit timeout yet).
- Marker CSVs (10-14 MB, ~41k rows) are downloaded, parsed, filtered and grouped in `public/js/siarhe-worker.js` (Web Worker, URL passed via `data-worker`); `loadMarkerData` in `siarhe-controls.js` falls back to the main-thread path (`d3.csv`) if workers are unavailable or fail. Both paths must keep the same filtering/grouping logic. The static-base CSV (small) and GeoJSON still load on the main thread.
- Large data files (>= 100 KB) are read from a copy (`*.geojson.json` / `*.csv.txt`, made by `siarhe_data_read_url()` / `siarhe_build_read_copy()` in `includes/helpers.php`) because many servers serve `.csv`/`.geojson` as `application/octet-stream` and do not compress them; the original stays untouched (backups, versions, download). Option `siarhe_read_copies` turns it off.
- Marker rendering: all active markers (`posicion`, `espectro` bubbles and `spike`) use ONE `<canvas>` (`app.map._cv*` in `siarhe-map.js`: cached sprites for symbols/bubbles (bubble sizes quantized in ~6 % steps), triangles drawn directly for spikes, `d3.quadtree` + per-shape hit tests for hover/click; stacking order = bubbles < spikes (north behind) < position, kept by the sort in `updateMarkers`) when more than `app.map.CANVAS_MIN` (3000; `CANVAS_MIN_TOUCH` 800) are active; below that, one SVG `<path>` per point (zoom refreshes only visible ones via `_refreshMarkerGeometry`, events delegated on the markers layer). Border width is in screen px (`_strokePx`, 0.4-1 px). `?siarhe_canvas=1|0` forces canvas on/off; `?siarhe_perf=1` logs timings to the console. Layer order inside `.siarhe-map-container`: main `<svg>` (polygons, labels, SVG markers) -> `<canvas>` -> overlay `<svg class="siarhe-overlay-svg">` (legends + measurement layer, same viewBox, follows the zoom transform) -> HTML controls. PNG export clones the main SVG and appends the overlay groups and the canvas points as vectors.
- Detailed layer (municipios / localidades view): `public/js/siarhe-geo-worker.js` downloads the GeoJSON (the national one is ~37 MB, 1.8M vertices), projects it (Mercator, same params as `state.projection`) and returns SVG path strings in 3 levels of detail (Douglas-Peucker 0.25 / 0.06 viewBox units / full); `app.map._locApplyLod` swaps the `d` of every polygon when the zoom crosses k=2.5 and k=10. Prepared features carry `properties`, `bounds` and `d[0..2]` (no geometry). Falls back to `d3.json` + `state.path` if the worker is unavailable or the projection is not reproducible (`app.controls.loadLocGeo`). The base (entities) layer is still projected on the main thread.
- Marker size is defined in SCREEN pixels (`app.map._markerMetrics`): cross width = 14 px (pc) / 15 (tablet) / 11 (phone) up to k=4, shrinking smoothly to 8 / 10 / 8 px at k=25 and staying there (never grows back). Device kind comes from the map container width (<520 phone, <900 or coarse pointer tablet) via `_deviceInfo`, not from `window.innerWidth`. Max zoom is `max(initialK*25, 50)` raised for the national map to ~30 m per pixel (`byResolution`, cap 400: ~110x PC, ~300x phone); canvas threshold is 3000 markers (800 on touch).
- Density markers are also in screen px (`_markerMetrics`): spike = semi-base/min height/max height 3.4/17/69 (pc), 3.4/18/74 (tablet), 2.4/11/46 (phone) with little zoom, growing smoothly (k 4 -> 25) to 4.5/22/88, 5/24/96 and 6/24/96; bubbles keep their area range but multiply it (linear x1.25 pc, x1.3 tablet, x1.35 phone at k>=25). Spike hit area is at least `spkHit` (5 px pc / 9 px touch) wide at the base (`_cvHit`).
